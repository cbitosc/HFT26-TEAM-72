# 📡 OFFGRID Mesh Network Wire Protocol Specification

Version: `1.0.0`  
Standard: `OFFGRID-RADIO-WIRE-V1`  
Scope: Peer-to-Peer Air-Gapped Disaster Communication  

---

## 1. Overview

The **OFFGRID Wire Protocol** defines the serialization, cryptographic envelope, and routing semantics used by OFFGRID nodes operating over peer-to-peer radio channels, including **Bluetooth Classic RFCOMM**, **Bluetooth Low Energy (BLE)**, and **Wi-Fi Direct TCP Sockets**.

Because OFFGRID operates in air-gapped emergency environments with **zero internet connectivity**, all communication relies on store-and-forward peer relays, cryptographic authenticity proofs, and multi-hop TTL tracking.

---

## 2. Wire Framing & Transport Encoding

### 2.1 Stream Transports (Bluetooth RFCOMM & Wi-Fi Direct TCP)
For stream-oriented transports, packets are serialized as UTF-8 encoded JSON strings delimited by a single newline character (`\n`, `0x0A`):

```
+-------------------------------------------------------------+------+
|                  UTF-8 Encoded JSON Packet                  | 0x0A |
+-------------------------------------------------------------+------+
```

- **Maximum Packet Size**: 1,048,576 bytes (1 MB) to accommodate voice clips.
- **Framing**: Readers buffer input streams until reaching `\n`, deserialize the JSON payload, verify HMAC signatures, and forward or dispatch.

### 2.2 Datagram & Beacon Transports (BLE Advertising)
- **Service UUID**: `6e7e9c64-75c2-4e7a-9c09-96e9914d873c` (General discovery)
- **Secure Service UUID**: `6e7e9c64-75c2-4e7a-9c09-96e9914d873d` (Paired RFCOMM listener)
- **Payload**: Advertises service UUID and localized device name prefix `OFFGRID-xxxx`.

## 3. Packet Schema

Each wire packet is represented as a JSON object with the following fields:

| Field | Type | Required | Description |
| :--- | :--- | :--- | :--- |
| `id` | `String` (UUIDv4) | Yes | Globally unique identifier generated by the originating node. |
| `sender` | `String` | Yes | Device or responder identifier originating the packet. |
| `priority` | `String` | Yes | Priority classification: `SOS`, `MEDICAL`, `GENERAL`, `RECEIPT`, or `RESPONDER`. |
| `body` | `String` | Yes | Ciphertext payload encrypted using AES-256-GCM (`v1:<base64>`). |
| `createdAt` | `Long` | Yes | Unix epoch timestamp in milliseconds when the packet was generated. |
| `ttl` | `Int` | Yes | Time-to-Live hop count (default: `5`). Decremented on each relay hop. |
| `hops` | `String` | Yes | Comma-delimited list of intermediate relay device IDs traversed. |
| `type` | `String` | Yes | Packet function: `MESSAGE`, `RECEIPT`, or `RESPONDER_ACK`. |
| `receiptFor` | `String` | No | Target message ID when confirming delivery receipt or responder ACK. |
| `auth` | `String` (Hex) | Yes | HMAC-SHA256 signature calculated over packet canonical signing string. |

### Example Wire Packet
```json
{
  "id": "e4f8d220-4a8b-4b21-826c-d2ff9bc6a982",
  "sender": "DEV-4819",
  "priority": "SOS",
  "body": "v1:aW5pdGlhbGl6YXRpb252ZWN0b3JmYWtlY2lwaGVydGV4dGRhdGE=",
  "createdAt": 1730332800000,
  "ttl": 4,
  "hops": "DEV-1024",
  "type": "MESSAGE",
  "receiptFor": null,
  "auth": "3b8a05c192f9e4210e5d168d4a7c1b0521ad879c5f891b93ef2d3c907b89d421"
}
```

## 4. Cryptographic Envelope

### 4.1 Key Derivation
All nodes participating in a disaster response network share an emergency group code (default or responder-configured).
- **Encryption Key**: First 16 bytes of `SHA-256(group_code)`.
- **HMAC Signing Key**: UTF-8 bytes of `group_code`.

### 4.2 Payload Encryption (AES-GCM)
1. Generate a cryptographically secure 12-byte random Initialization Vector (IV).
2. Encrypt cleartext with AES-GCM (128-bit authentication tag).
3. Prepend IV to ciphertext and encode in Base64:
   $$\text{body} = \text{"v1:"} + \text{Base64}(\text{IV} \parallel \text{Ciphertext})$$

### 4.3 Envelope Signing (HMAC-SHA256)
The canonical signing string is constructed by concatenating payload fields separated by pipe (`|`):
```
id | sender | priority | body | createdAt | ttl | hops | type | receiptFor
```
The signature is verified using constant-time string comparison to prevent side-channel timing attacks.

## 5. Multi-Hop Routing & Store-and-Forward Relay

```
[Origin Node] --(TTL=5)--> [Relay Node A] --(TTL=4)--> [Relay Node B] --(TTL=3)--> [Responder Node]
      ^                                                                                    |
      +----------------- (TYPE_RECEIPT / TYPE_RESPONDER_ACK) <-----------------------------+
```

1. **Origin Transmission**:
   - Outgoing packet assigned initial `ttl = 5`, saved to local `MessageStore` as `PENDING`.
   - Forwarded to all currently connected peers.
2. **Relay Processing**:
   - Node checks `seen.add(packet.id)`. If duplicate, drop immediately.
   - Node verifies HMAC-SHA256 signature. If invalid, drop immediately.
   - If `ttl <= 1`, node delivers locally but does not relay further.
   - Otherwise, node produces `forwarded = packet.forwardThrough(localDeviceId)` (`ttl` decremented, `localDeviceId` appended to `hops`), signs, and relays to all connected peers except incoming sender.
3. **Delivery Acknowledgments**:
   - `TYPE_RECEIPT`: Broadcast by every node upon successfully receiving and decoding a packet.
   - `TYPE_RESPONDER_ACK`: Broadcast specifically by nodes running in Responder Gateway mode.
